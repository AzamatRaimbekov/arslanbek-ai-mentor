# Наблюдения о развитии

В сводке дополнительно передавай `learning_evidence` и `tool_usage`. Схема —
`scripts/progress_report.py:SCHEMA`, учебный пример — `progress-example.json`.
Нет наблюдения — пустой список или unknown, а не предположение об уровне.

`learning_evidence` содержит конкретные эпизоды по направлениям:
prompt_engineering, context_engineering, harness, skill_authoring,
plugin_authoring, frontend, backend, databases, testing, devops, security.
Укажи `competency_id`, `state` (unknown / practiced / demonstrated /
needs_practice), `actor` (learner / agent / together / unknown), `evidence_type`
(learner_action / learner_explanation / artifact_check / mentor_observation),
фактическое `evidence` и проверяемый `next_action`.

Demonstrated — только самостоятельное действие или объяснение ученика.
Созданный тобой код не подтверждает его самостоятельный навык. Кабинет связывает
подтверждения по разным целям и проектам: сохраняй цель, не меняй её ради счётчика.
Сравнивай конкретные эпизоды; не выдумывай проценты развития и рейтинги.

Для промпт-инжиниринга наблюдай формулирование цели, ограничений, примеров и
критерия проверки. Для контекст-инжиниринга — выбор релевантных источников,
обновление инструкций и исключение лишнего или чувствительного из контекста.
Харнес — инструкции, инструменты, хуки, тесты и управление работой агента.
Наличие конфигурации отдельно от умения объяснить и применить её.

В `tool_usage` включай действительно использованные, созданные или настроенные
инструменты: `kind` (skill / plugin / mcp / harness / tool), короткое `tool_id`,
`action` (used / created / configured), `actor` и `evidence`. Если делал агент,
так и запиши. Создание требует проверки артефакта, одно упоминание не доказательство.
Команды, аргументы, результаты инструментов, тела файлов, секреты и абсолютные
пути в эти метаданные не включай.

## Автоматические события

Теги тем и намерений определяются по словам текущего промпта. Это ориентир
для поиска, не оценка навыка. Снимок выбранного приложения и текущего проекта
передаёт имена скиллов, включённых плагинов и MCP, наличие инструкций, хуков,
контроля версий, тестов и CI. Тела скиллов и значения конфигурации не загружаются.
Сканирования всей машины или чужих приложений нет; список ограничен 64 элементами.
В общем MCP/Claude Desktop настройки других приложений не считываются.
Доступно не означает использовано.
В общем MCP и Claude Desktop нет достоверного пути рабочего проекта: автоматический
снимок среды недоступен, эти сведения берутся только из наблюдений наставника.

PostToolUse в Claude Code и доверенные хуки Codex фиксируют названия инструментов.
Claude Code передаёт локальному обработчику аргументы и результат: обработчик
проверяет признаки чувствительных данных и отбрасывает содержимое. В Codex хук
передаёт только имена; аргументы и результаты этим обработчиком не проверяются.
В приложениях без хуков наблюдения зависят от инструментов и сводок агента;
полную историю обещать нельзя. Старые разговоры не считывай.

## Сигналы конфиденциальности

Детектор передаёт только категорию, количество и серьёзность: ключи, токены,
приватные ключи, пароли, возможные платёжные идентификаторы и конфиденциальные
метки. Контактные данные — информационные признаки, без тревожного уведомления.
Секреты или фрагменты не попадают в сигнал и не возвращаются через восстановление.
Преподаватель отмечает проверку или ложное срабатывание в кабинете.

Дополнительные метки школы задаются в текущем проекте:
`.arslanbek/privacy-policy.json`: `{"markers": ["внутренний проект Example"]}`.
Они проверяются в промптах. Не помещай в метки пароли или личные данные.
Это дополнительная настройка, не обязательный шаг установки ученика.

Сигнал не доказывает утечку или передачу определённому сервису. Скилл не видит
все вложения и каналы, не является сетевым прокси. Очистка отчётности не очищает
исходный чат модели. Помоги проверить ситуацию без повторения секрета;
подтверждённый ключ или пароль заменяет владелец сервиса.
