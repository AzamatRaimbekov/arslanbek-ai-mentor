# Кабинет школы: запуск и сводки

## Состояние

Текущий режим — кабинет и сбор сводок скилла в Railway. Внешний серверный
ИИ-анализ выключен через `AI_ANALYSIS_ENABLED=false`; ключ провайдера не нужен.
Сводку пишет наставник внутри рабочей сессии, сервер хранит и показывает её.

- Кабинет: https://frontend-production-a08a.up.railway.app
- Сервер: https://backend-production-9ce9c.up.railway.app
- Railway-проект и ID сервисов: `railway/project.json`.
- Логин и пароль администратора: локальный `backend/.env.railway-login.txt`,
  права 0600. Этот файл и `.env.railway.json` исключены из Git и публикации.
- Готовый пакет скилла: раздел «Подключение» кабинета. Установка — распаковать
  архив, поместить папку `arslanbek-ai-mentor` в `~/.claude/skills/` и вызвать скилл.
  При загрузке автоматически выполняется `scripts/bootstrap.py`: подключаются
  хуки и узкие разрешения на команды отчётности. `school-policy.json` в архиве
  задаёт передачу по ранее оформленному договору: отдельного вопроса нет,
  первая регистрация и отправка происходят автоматически.
  Основание в локальной записи — `source=school_contract`; `activated_at` хранит
  дату подключения, `ts=null` не имитирует подпись или дату договора.
  Сохранённое отключение не переопределяется. Наставник уведомляет о передаче.
  В первой сессии текущие запросы передаёт агент; после загрузки хуков используется
  автоматический сбор без двойной записи. Для обновления агент выполняет `install.py --setup-only`,
  сохраняя личные файлы, настройки и выбор. Интерактивный `install.py` остаётся
  дополнительным вариантом установки; `--choose-collection` меняет выбор.
- Новое согласие v3 разрешает сбор для школы, `analysis_allowed=false`.
  Согласия v1/v2 на такой же сбор принимаются без расширения их назначения.
- Сводки видны общей лентой «Сводки» и в карточке участника во вкладке «Прогресс».
- Обновления школьного пакета выполняются повторной установкой из кабинета;
  автоматическое обновление этого пакета с GitHub отключено, чтобы старая
  опубликованная версия не перезаписала рабочие настройки.

## Поддержка приложений и подробный прогресс

- Claude Code: прежняя установка и события `UserPromptSubmit` / `SessionStart`.
- Codex: `python3 install.py --client codex`; скилл в `~/.agents/skills`,
  хуки в `~/.codex/hooks.json`, MCP в `~/.codex/config.toml`. Codex требует
  обзора и доверия хуков в своём интерфейсе; установщик не обходит этот контроль.
- Другие приложения: `python3 install.py --client mcp`; локальный stdio MCP
  (`scripts/mcp-server.py`) и переносимый `SKILL.md`. Модель, в том числе DeepSeek,
  выбирается приложением. Без хуков каждый запрос передаёт агент инструментом;
  полнота истории не гарантируется. Обычный чат без интеграций не поддерживается.
- Идентификатор устройства общий; очереди, статусы и выбор сбора разделены
  по приложениям. Новое приложение не наследует локальное согласие Claude Code.
- Подробная сводка: JSON v1 из `references/progress-report.md`. В ней задача,
  цель, текущий этап, направления, действия сотрудника и ИИ, наблюдения навыков
  с основаниями, проверки, препятствия, следующий шаг и критерий готовности.
  Сервер не генерирует выводы и не назначает оценку при отсутствии данных.
- Миграция `0005_multiclient_progress.sql` добавляет источник и JSON-сводку,
  проверяет структуру, сохраняет совместимость старых клиентов, дедупликацию
  и порядок событий. Публиковать backend перед новым frontend/архивом.
- В карточке показана последняя актуальная сводка; предыдущие — во вкладке
  «Прогресс». Старые текстовые профили отображаются разделами, а не исходным Markdown.

Официальные интерфейсы: [Codex skills](https://learn.chatgpt.com/docs/build-skills),
[Codex hooks](https://learn.chatgpt.com/docs/hooks),
[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli),
[MCP stdio](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Наблюдения о развитии: выпуск 9.0.0

В карточке ученика доступны «Развитие», «Инструменты», «Промпты» и «Защита
данных» с периодами 14, 30 и 90 дней. Карта охватывает 11 направлений: промпты,
контекст, харнес, создание скиллов и плагинов, frontend, backend, базы данных,
тестирование, DevOps и безопасность. Каждое наблюдение связано с исходной
сводкой, датой и исполнителем. Самостоятельные подтверждения учитываются по
разным целям и проектам; это наблюдения наставника для проверки преподавателем.

Обновлённый скилл добавляет теги к новым промптам, ограниченный снимок выбранной
рабочей среды и события инструментов. Наличие конфигурации, применение и
создание показаны отдельно. Старые сводки остаются доступными; им не назначаются
задним числом самостоятельные действия, новые события или сигналы секретов.
Подробные правила и ограничения — `skills/arslanbek-ai-mentor/references/observability.md`.

Детектор локально проверяет промпты и, в Claude Code, данные событий инструментов.
В Codex событие содержит только имя: содержимое инструментов этим хуком не
проверяется. В общем MCP и Claude Desktop сбор зависит от вызовов агента;
достоверный автоматический снимок проекта недоступен. Сервер получает только
категорию, серьёзность и количество признаков для сигнала. Аргументы и результаты
инструментов не загружаются. Сигнал означает возможный риск, а не доказанную
утечку; очистка школьной отчётности не перехватывает исходный чат модели.

Уведомления доступны внутри кабинета, открытые сигналы проверяются преподавателем
и отмечаются как рассмотренные или ложные срабатывания. Решения сохраняются в
аудите. Внешние каналы уведомлений в этом выпуске не настроены.

Миграция `0006_student_observability.sql` опубликована перед новым frontend.
Она добавляет метаданные промптов, события инструментов, сигналы и агрегаты
карточки. Чтение и обработка доступны администраторам; повторная доставка не
увеличивает счётчики и не переписывает исходное наблюдение. Применённые миграции
не изменять: bootstrap проверяет их контрольные суммы.

Манифест публикации — `railway/releases/observability-2026-10-08.json`.
Проверки рабочего сайта выполнялись без создания учебных или тестовых записей.

## Повторная публикация Railway

`python3 backend/railway/configure.py` повторно использует сохранённые секреты,
настраивает переменные и проверки готовности backend/frontend/auth/rest.
Не удалять `.env.railway.json`: это привело бы к генерации новых ключей.

После изменения скилла: `python3 backend/railway/package-skill.py`.
Команда собирает архив с публичным адресом и anon-ключом; личные наблюдения и
закрытые ключи в пакет не входят. Для обновления сервиса используйте
`railway up --project <projectId> --environment <environmentId> --service <name>
--detach --path-as-root <directory>` из корня репозитория. Каталоги:
`backend`, `dashboard`, `backend/railway/auth`, `backend/railway/rest`.

Проверки после публикации:

```bash
python3 backend/railway/smoke.py
cd dashboard
node tests/production-smoke.mjs
```

Первая проверяет здоровье, настоящий вход, запрет анонимного чтения, запрос
ленты сводок и статистику без создания записей. Вторая открывает опубликованный
кабинет в браузере, проверяет вход, сводки, контрольную сумму скачанного скилла
и выход. Полный `smoke.py --delivery` дополнительно требует зарегистрированного
Railway SSH-ключа: проверяет доставку синтетической записи и удаляет только её.
В этом запуске полный тест доставки не выполнен: SSH-ключ не зарегистрирован;
синтетические записи не создавались. Проверка реального участника остаётся
следующим шагом после установки скилла и его согласия.

Дашборд работает только с подключённой базой Supabase. Демонстрационного режима
нет; при отсутствующих настройках показан экран подключения.

## Альтернативный запуск в Supabase с внешним анализом

Этот раздел относится к прежнему варианту архитектуры. В текущем Railway-запуске
внешний анализ не используется; не включать его без отдельной задачи.

1. Выбрать проект Supabase и email администратора. Для доступа агента можно
   подключить Supabase к приложению, либо использовать Supabase CLI после входа.
   API-ключи держать в локальных файлах/секретах сервера, не в чате и не в Git.
2. Скопировать `backend/.env.example` в `backend/.env.local`, заполнить поля.
   `SUPABASE_ANON_KEY` — публичный anon / publishable ключ, **не service_role**.
3. Проверить и распространить только публичные параметры:

```bash
python3 backend/configure-production.py
python3 backend/configure-production.py --write
```

Вторая команда создаёт `dashboard/.env.local` и обновляет публичный `telemetry.conf`
в скилле. Проверяет совпадение project ref и URL, отклоняет секретный ключ для
браузера. Не выводит ключи, не отправляет запросы и не создаёт администратора.

4. Применить миграции `0001` → `0004` из `backend/supabase/migrations`. Уже
   применённые миграции повторно не запускать. Если исходная схема создавалась
   вручную через SQL Editor, сначала сверить её с журналом миграций CLI.
5. Создать подтверждённого пользователя с паролем в Supabase Auth и включить в `admins`:

```sql
insert into public.admins(user_id,email)
select id,email from auth.users where email='YOUR_ADMIN_EMAIL'
on conflict(user_id) do nothing;
```

6. В Supabase → Edge Functions → Secrets задать `OPENAI_API_KEY`, `AI_MODEL` и
   `ALLOWED_ORIGINS` (адрес дашборда с протоколом, без завершающего `/`; несколько
   адресов через запятую). Модель должна поддерживать Responses API и строгий JSON
   schema output. Выбор модели оставлен настройкой, платных запросов при разработке
   не было. Текущий адаптер — **OpenAI API**; другой провайдер требует адаптера.
   `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` доступны функции
   в стандартном окружении Supabase. Последний используется только сервером.
7. Опубликовать функцию из каталога `backend` после подключения CLI к проекту:

```bash
cd backend
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase functions deploy analyze-team
```

Проверка JWT включена в `supabase/config.toml`. Функция дополнительно проверяет
пользователя через Auth и членство в `admins`, прежде чем читать снимок или
вызывать ИИ. Не выключать проверку администратора для устранения 401/403.

8. Собрать `dashboard` с `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`; опубликовать `dist` на выбранном статическом хостинге.
   Вход выполняется паролем, без самостоятельной регистрации пользователей.
   Задать окончательный URL в `ALLOWED_ORIGINS` до запуска анализа.
9. Выпустить обновлённый скилл вместе с публичным `telemetry.conf`. Одной публикации
   дашборда недостаточно: старые копии скилла с пустым адресом не отправят данные.

## Проверка одного реального участника

1. На машине участника обновить скилл и выполнить:

```bash
python3 ~/.claude/skills/arslanbek-ai-mentor/scripts/install-telemetry-hooks.py
```

Команда добавляет `UserPromptSubmit` и асинхронный `SessionStart`, сохраняя остальные
настройки Claude Code. Встроена также в `ensure-tools.sh`; повторный запуск не
дублирует команды. Перезапустить сессию Claude Code.

2. На первом промпте скилл объясняет сбор и внешний ИИ-анализ. **Участник сам решает,
согласен ли он.** Агент запускает `consent.sh yes` только после ответа. Согласие
версии 1 требует обновлённого вопроса. Не включать согласие коллегам удалённо.
3. Участник выполняет одну настоящую задачу. После нескольких промптов наставник
готовит срез по `references/honest-reporting.md`. Не создавать фиктивные успехи.
4. Проверить доставку, не печатая персональные данные и секрет устройства:

```bash
python3 ~/.claude/skills/arslanbek-ai-mentor/scripts/telemetry.py flush
python3 ~/.claude/skills/arslanbek-ai-mentor/scripts/telemetry.py status
```

Сверить успешную доставку, пустую очередь и записи в дашборде: промпт, время,
проект, срез. `report.sh` подтверждает только локальную очередь, не доставку.
5. В «Анализ команды» сформировать отчёт. Проверить каждый вывод по источникам.
Первый настоящий ответ модели оценивается наставником перед использованием.

## Что считается честным анализом

- Счётчики за период считает база. ИИ видит **выборку** до 8 промптов и 5 срезов
  на устройство, распределённую по временным корзинам; длинный текст сокращается.
  Отчёт показывает, сколько записей прочитано из общего количества.
- В анализ входят только устройства с `analysis_allowed=true` после согласия v2.
  Остальные считаются исключёнными. При более 50 подходящих устройств или слишком
  большом входе сервер просит выбрать меньшую группу и не отбрасывает людей молча.
- Каждому выводу нужны существующие ссылки на источники. Проверяется присутствие
  всех участников, принадлежность источников конкретному человеку и отсутствие
  персональных выводов при нуле событий. Ошибка проверки даёт статус `failed`.
- Наблюдения и интерпретации отделены. Срез другого ИИ — оценка, не независимая
  проверка. Сообщение «я запустил тесты» не превращается в доказательство тестов.
- Нет рейтинга сотрудников, расчёта часов, выводов о мотивации или кадровых
  рекомендаций. Количество промптов не является оценкой продуктивности.
- ИИ может ошибиться даже с корректной ссылкой. Структурная проверка не доказывает
  смысловую правильность вывода; наставник может открыть сохранённый источник.
- При пустом входе платная модель не вызывается, сохраняется `insufficient_data`.
  При ошибке API выдуманный отчёт не показывается. Повторный запуск — не чаще
  одного раза в две минуты на администратора, включая параллельные запросы.
- Снимок источников, версия инструкции, модель, период, время и usage хранятся
  вместе с отчётом. Имена из карточки, email, организация и данные устройства
  не включаются в структурированный запрос модели: участники заменены псевдонимами.
  Сами отрывки могут содержать личные упоминания; регулярные выражения скрывают
  типовые секреты/email, но не гарантируют удаление всех персональных данных.

## Доставка и ограничения

События имеют устойчивые UUID. Повтор отправки после потери ответа не создаёт
дубликаты и не увеличивает счётчики. Время среза берётся с машины ученика;
отложенная отправка старого среза не затирает новый. Время приёма хранится отдельно.
Точность времени зависит от часов устройства. Старые клиенты без UUID не получают
защиту от дублей — для неё нужно обновление скилла.

Статус устройства показывает последнюю успешную доставку и безопасный код ошибки.
При отключении сбора промпты и срезы не записываются. `consent.sh no` очищает
локальную очередь и отправляет отзыв допуска к будущему анализу; без сети отзыв
ожидает следующего запуска. Пока отзыв не доставлен, сервер не знает об отключении.
Уже доставленные записи и ранее созданные отчёты автоматически не удаляются.

`last_seen` — последняя передача данных, а не достоверное время работы человека.
Один человек с несколькими устройствами может иметь несколько записей.
Публичный endpoint предназначен для сбора, а не подтверждения личности сотрудника:
имена/email от клиента сами по себе не подтверждают личность. Перед кадровыми или
иными значимыми решениями нужно отдельно сверять источник и личность.

## Проверки без доступа к продакшену

### Настольные пакеты 8.1

Для публикации скачиваний запускайте `python3 backend/railway/package-desktop.py`
из корня репозитория. Этот сборщик включает актуальную приватность v8 и создаёт
в `dashboard/public/downloads` три файла и `release.json` с SHA-256:

- `arslanbek-ai-mentor.zip` — Claude Code и вкладка Code в Claude Desktop;
- `arslanbek-codex.zip` — Codex Desktop/CLI, переносимый SKILL.md и маркер клиента;
- `arslanbek-claude-desktop.mcpb` — обычный чат Claude Desktop, MCPB 0.4 с UV.

Оба ZIP содержат проверенный по SHA-256 Python 3.14.8 для Windows x64 и ARM64.
MCPB запускает Python через среду, управляемую приложением. В macOS/Linux для
ZIP нужен Python 3.10+. Не публикуйте сборку с `--without-windows-runtime`:
она предназначена только для быстрых тестов. Отдельный `package-skill.py`
создаёт базовый архив и не заменяет финальный сборщик настольных пакетов.

Сотрудник копирует скилл и вызывает его, агент сам выполняет bootstrap. В обычном
чате Claude устанавливается расширение. Доверие хукам в Codex остаётся требованием
приложения. Хуки записывают новые запросы, сводку составляет агент. Обычный чат
Claude Desktop не предоставляет хук каждого сообщения: полнота зависит от
вызовов MCP-инструментов. Локальная установка не подключает удалённые сессии.

Проверены 56 Python-тестов, 10 браузерных сценариев, официальный валидатор MCPB
2.1.2 и запуск расширения через UV. Тесты включают отдельное состояние каждого
клиента, UTF-8 при заданной cp1252, пути с кириллицей/пробелами/апострофом,
сохранение других хуков, повторную установку и отключение сбора. Проверка
выбора Windows runtime симулирует ОС; запуск python.exe и GUI настольных
приложений на настоящем Windows-компьютере ещё не выполнен.

```bash
python3 -B -m unittest discover -s backend/tests -v
cd dashboard
```
